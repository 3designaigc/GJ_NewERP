# 高玉ERP備案整體系統架構

建立日期：2026-06-14

## 1. 系統定位

高玉ERP備案不是單一表格，而是把目前分散在商品主檔、供應商資料、報價資料、成本公式、現金流、文件追蹤、船班追蹤與 TDS 待辦中的小系統，整理成同一個工作平台。

第一階段的目標是：

- 讓現有 JSON 資料可以被統一查詢
- 先建立商品、報價、供應商、PO 追蹤與現金流的主架構
- 讓不同角色看到不同資料
- 保留原始 JSON 作為資料備援與轉正式資料庫的基礎

### 4.1.2 台幣成本與到倉價工作規範

目前資料中已存在台幣成本與到倉價相關欄位，但原架構文件尚未把工作規則寫清楚。正式系統必須把「外幣報價」與「台幣到倉價報價」分開管理。

#### 目前資料欄位

來源：

- `products_final.json`
- `twd_formula_config.json`

商品主檔已存在欄位：

| 欄位 | 說明 |
|---|---|
| `台幣總成本` | 依公式或手動資料核算出的台幣到倉總成本 |
| `台幣最低報價` | 台幣到倉最低報價 |
| `台幣10%底線` | 台幣底線價 |
| `台幣最低報價匯率` | 使用的匯率，例如 EUR 37.7 |
| `台幣價來源` | 公式、手動成交價或其他來源 |
| `報價交易條件` | CIF、EXW、FOB、到倉價等 |

`twd_formula_config.json` 已定義冷凍與部分供應商的台幣核算公式，包含：

- 匯率
- 海運費
- TDS 佣金
- 關稅
- VAT / 清關
- 冷凍倉儲
- 內陸運費
- 中文標籤
- 檢驗費
- 利潤率

#### 哪些產品需要核算台幣成本

第一階段判定規則：

- `報價交易條件` 等於 `到倉價`
- 或 `台幣價來源` 有值
- 或 `台幣總成本`、`台幣最低報價`、`台幣10%底線` 任一欄位大於 0
- 或供應商存在於 `twd_formula_config.json`
- 或商品屬於需要台幣到倉價報價的客戶 / 通路

目前資料中已有 231 筆商品具備台幣成本或台幣報價資料，主要集中在冷凍與需到倉價報價的品項。

#### 台幣成本核算流程

```text
外幣成本 / 報價條件
        ↓
判斷成本基準 EXW / FOB / CIF
        ↓
加計海運、TDS佣金、關稅、VAT、清關
        ↓
加計冷凍倉儲、內陸運費、中文標、檢驗費
        ↓
得到台幣總成本 / 到倉成本
        ↓
依利潤率得到台幣最低報價
        ↓
產出台幣底線與可報價版本
```

#### 客戶 / 通路報價限制

有些客戶或通路不能直接報外幣成本或外幣底線，只能使用台幣到倉價報價。正式系統應建立 `customer_quote_rules`。

建議規則欄位：

| 欄位 | 說明 |
|---|---|
| `customer` | 客戶名稱 |
| `channel` | 通路，例如 PX Mart、好市多、全通路 |
| `allowed_quote_currency` | 允許報價幣別，例如 TWD only、Foreign allowed |
| `required_price_basis` | 必須使用的價格基準，例如 到倉價、CIF、EXW |
| `allow_foreign_quote` | 是否允許外幣報價 |
| `allow_cost_visibility` | 是否允許看到成本 |
| `approval_required` | 是否需要本人核准 |

第一階段系統規則：

- 若客戶 / 通路設定為 `TWD only`，業務只能看到 `台幣最低報價` 與 `台幣10%底線`。
- 若商品 `報價交易條件 = 到倉價`，報價時應優先使用台幣到倉價。
- 若商品沒有台幣成本資料，系統應標示「需核算台幣成本」，不得直接對客戶報價。
- 若 `台幣價來源 = 手動成交價`，應顯示來源並保留人工確認狀態。
- 若 `台幣價來源 = 公式`，應保留公式版本、匯率與計算日期。

#### 報價禁止事項

以下情況正式系統應阻擋或要求本人確認：

- TWD only 客戶使用外幣報價
- 到倉價客戶使用 EXW / FOB 價格直接報價
- 台幣總成本為 0 但仍產生台幣報價
- 匯率空白或公式版本不明
- 報價低於台幣底線
- 報價來源不明

#### 畫面呈現

商品列表與商品詳情頁應分開顯示：

- 外幣成本
- 外幣報價
- 外幣底線
- 台幣到倉成本
- 台幣到倉報價
- 台幣底線
- 台幣價來源
- 匯率與公式版本

目前原型商品表已加入台幣到倉成本、台幣到倉報價、台幣底線與台幣價來源欄位。正式系統下一步要把「客戶選擇」加入報價流程，讓系統自動判斷該客戶可用哪一種報價。

### 4.1.3 好市多專案工作規範

好市多專案目前散落在商品主檔的 `適用通路`、`郵件來源` 與供應商資料中。正式系統應把好市多視為獨立專案類型，而不是只當作一般通路文字。

#### 好市多商品判定

第一階段判定規則：

- `適用通路` 包含 `好市多`
- 或商品屬於經確認的好市多專案清單

目前資料中可直接辨識：

- `好市多`
- `好市多烘焙專案`

注意：`郵件來源` 中出現「好市多對標」不一定代表該商品是好市多專案商品，可能只是參考或對標報價。正式系統應區分：

- 好市多正式提案
- 好市多對標資料
- 好市多已進案商品
- 好市多未採用 / 參考商品

#### 好市多專案欄位

建議新增欄位：

| 欄位 | 說明 |
|---|---|
| `project_type` | 專案類型，例如 Costco、PX Mart、全通路 |
| `project_status` | 提案中、送樣中、報價中、待回覆、已採用、未採用 |
| `costco_item_type` | 一般商品、烘焙專案、對標品、季節商品 |
| `buyer_contact` | 好市多窗口 |
| `sample_status` | 未送樣、已送樣、待回饋、通過、不通過 |
| `quote_deadline` | 報價截止日 |
| `target_landed_cost` | 目標到倉成本 |
| `target_sell_price` | 目標售價 |
| `case_pack` | 箱規 |
| `pallet_info` | 棧板規格與箱/板 |
| `project_notes` | 專案備註 |

#### 好市多專案流程

```text
來源郵件 / 供應商報價
        ↓
建立好市多專案商品
        ↓
確認箱規、箱入數、棧板、BBD、條碼
        ↓
建立報價與報價底線
        ↓
送樣 / 提案
        ↓
好市多回覆
        ↓
轉正式 PO 或標記未採用
        ↓
進入文件、船班、應收應付流程
```

#### 好市多專案權限

目前業務帳號 `sales` 可看：

- 所有冷凍品
- `適用通路` 包含 `好市多` 的商品

後續正式化時，應改成 `product_visibility_rules`，不要只靠文字判斷。

### 4.5.1 進出口文件工作規範

- `文件核對.json`

這些資料已經不是單純備註，而是進出口文件作業的初版 SOP。

#### 文件清單

`文件核對.json` 目前定義的核對文件：

| 文件代碼 | 文件名稱 | 用途 |
|---|---|---|
| `PI` | Proforma Invoice / 形式發票 | 下單與價格確認 |
| `PL` | Packing List / 裝箱單 | 箱數、重量、棧板與包裝核對 |
| `COO` | Certificate of Origin / 產地證明 | 產地與報關文件 |
| `CI` | Commercial Invoice / 商業發票 | 報關與付款依據 |
| `HC` | Health Certificate / 衛生證明 | 食品進口必要文件之一 |

`文件追蹤.json` 目前另有追蹤：

| 文件代碼 | 文件名稱 |
|---|---|
| `BL` | Bill of Lading / 提單 |
| `COA` | Certificate of Analysis / 分析證明 |

正式系統應支援不同商品類型需要不同文件，例如酒類、食品、冷凍、常溫、非食品。

#### 文件核對欄位

目前核對欄位：

- 條碼
- 品名
- 重量
- 效期
- 收貨人

正式系統建議增加：

- PO 號
- 箱數
- 箱入數
- 總數量
- Gross weight
- Net weight
- 棧板數
- 製造商
- 產地
- 船名 / 航次
- B/L 號碼
- ETD / ETA
- 文件版本

#### 文件狀態

目前 `文件核對.json` 狀態：

| 狀態 | 說明 |
|---|---|
| 待提供 | 尚未收到 |
| 已收 | 收到待核對 |
| 核對中 | 核對進行中 |
| 通過 | 核對無誤已歸檔 |
| 不符 | 與 PO 或其他文件不一致 |

目前 `文件追蹤.json` 狀態符號：

| 符號 | 說明 |
|---|---|
| `✓` | 已收到 |
| `⏳` | 處理中或草稿 |
| `⚠️` | 有錯或不一致 |
| `❌` | 缺件或未到 |
| 空白 | 未知 |

正式系統應把符號轉成標準狀態碼，避免資料查詢與篩選時出錯。

#### 文件作業流程

```text
PO 建立
  ↓
PI 收到並核對價格、品名、規格、數量
  ↓
出貨前追 CI / PL / COO / HC / COA
  ↓
出貨後追 B/L
  ↓
核對文件彼此一致
  ↓
發現不符，退供應商或 TDS 修正
  ↓
通過後歸檔 Google Drive
  ↓
交報關 / 付款 / 到港追蹤
```

#### 文件不符處理規範

如果出現 `不符` 或 `⚠️`：

1. 系統標記異常欄位，例如品名、重量、效期、收貨人、Gross weight。
2. 填寫不符原因。
3. 指派窗口，例如 TDS Mirko、供應商、報關 Apollo。
4. 建立催件或修正待辦。
5. 收到新版文件後保留版本紀錄。
6. 核對通過後才能標記歸檔。

## 10. 決策重點

目前最重要的決策不是畫面，而是資料主軸：

- 商品以 `products_final.json` 為核心
- 報價以 `sales_d3.json` 與商品價格欄位整合
- 供應商以 `supplier_master.json` 為核心
- PO 以文件、船班、現金流共同串接
- 權限必須從一開始就跟資料表設計一起做

如果這個方向確認，下一步應該開始做正式資料庫 schema，而不是繼續只在 JSON 上追加功能。
